# Knowledge / RAG 配置项说明

> 来源：根据 Dify 知识库导入流程中的“文本分段与清洗”和“检索设置”页面截图整理。本文后续会作为知识库材料导入，用于验证能否通过 RAG 搜索到配置解释。

## 1. 文本分段与清洗

文本分段与清洗决定了原始文档如何被拆成知识库 chunk，以及这些 chunk 在向量化前如何被预处理。这个阶段会直接影响后续检索命中质量。

## 1.1 分段模式

### 通用

截图中选择的是“通用”分段模式。

含义：

- 通用文本分块模式。
- 检索和召回使用相同的 chunk。
- 适合 Markdown、普通技术文档、学习笔记、产品说明等常规文本。

适合当前场景：

- `dify-rag-lab/docs/` 下的学习文档都是 Markdown。
- 文档本身有标题、列表、代码块和说明文字。
- 第一轮 RAG 实验优先使用通用模式，方便观察默认切片效果。

### 父子分段

截图中也展示了“父子分段”选项，但当前未选择。

含义：

- 子块用于检索。
- 父块作为上下文提供给模型。
- 通常用于既希望精确命中，又希望回答时保留更大上下文的场景。

适合场景：

- 长文档。
- 章节结构明显的文档。
- 一个小片段被命中后，需要把所在章节一起提供给模型。

当前建议：

- 第一轮先不用父子分段。
- 等通用分段跑通后，再用同一批文档对比父子分段召回效果。

## 1.2 分段标识符

截图中的分段标识符是：

```text
\n\n
```

含义：

- 用两个换行作为优先分段边界。
- Markdown 中两个换行通常代表段落分隔。
- Dify 会尽量按段落切开，而不是在句子中间硬切。

对 Markdown 的影响：

- 标题和标题下的段落可能被分开。
- 短段落会形成较短 chunk。
- 如果 Markdown 中有很多空行，chunk 会更碎。

当前观察：

- 截图预览中出现了很多短 chunk，例如 `Chunk-3` 只有 7 characters，`Chunk-5` 只有 11 characters。
- 这说明当前文档按 `\n\n` 切分后，部分标题或短句被单独切成了很小的 chunk。

可能问题：

- 太短的 chunk 语义信息不足，向量检索时可能不稳定。
- 标题和正文分离后，检索命中标题时上下文不足。

后续实验：

- 保持默认分段，先完成第一次索引。
- 观察检索是否命中大量短 chunk。
- 如效果不好，再调整分段最大长度、重叠长度或尝试父子分段。

## 1.3 分段最大长度

截图中的分段最大长度是：

```text
1024 characters
```

含义：

- 单个 chunk 的最大字符数。
- 当文本段落超过该长度时，会继续切分。

影响：

- 值越小，chunk 越短，检索更细，但上下文更少。
- 值越大，chunk 越长，上下文更完整，但可能包含太多无关信息。

当前建议：

- 对当前学习文档来说，`1024 characters` 是合理的起点。
- 如果检索结果太碎，可以适当增大。
- 如果命中片段太宽泛，可以适当减小。

## 1.4 分段重叠长度

截图中的分段重叠长度是：

```text
50 characters
```

含义：

- 相邻 chunk 之间保留一部分重复文本。
- 用于避免关键信息刚好被切在两个 chunk 边界上。

影响：

- 重叠越大，上下文连续性越好。
- 重叠越大，索引体积和 token 成本可能越高。

当前建议：

- `50 characters` 适合作为第一轮默认值。
- 如果发现一个概念经常被切断，可以提高重叠长度。

## 1.5 文本预处理规则

截图中有两个预处理选项：

### 替换掉连续的空格、换行符和制表符

当前已勾选。

含义：

- 清理多余空白。
- 让文本更紧凑。
- 减少因为格式空白导致的无效 token。

适合当前场景：

- Markdown 文档可能包含列表缩进、空行、代码块。
- 该选项能减少无意义空白。

注意：

- 如果文档依赖缩进表达结构，例如代码块，过度清洗可能影响可读性。
- 当前第一轮可保持开启。

### 删除所有 URL 和电子邮件地址

当前未勾选。

含义：

- 删除文档中的链接和邮箱。

当前建议：

- 不建议勾选。
- 当前学习文档里可能记录 API URL、WebApp URL、Base URL、接口路径等关键信息。
- 如果删除 URL，会影响后续查询“API Base URL 是什么”“接口地址是什么”等问题。

## 1.6 摘要自动生成

截图中“摘要自动生成”处于关闭状态。

含义：

- 如果开启，Dify 会为文档或 chunk 自动生成摘要。
- 摘要可以帮助后续检索或展示。

当前建议：

- 第一轮先关闭，减少变量。
- 先观察原始 chunk 的检索效果。
- 后续可以开启后对比召回质量和成本。

### 摘要自动生成相关报错

在追加第二个文档时，曾遇到 `POST /console/api/datasets/indexing-estimate` 报错：

```text
Input tag 'None' found using 'enable' does not match any of the expected tags: False, True
```

对应请求体中出现了：

```json
"summary_index_setting": {
  "enable": null,
  "model_name": null,
  "model_provider_name": null,
  "summary_prompt": null
}
```

原因：

- 后端的 `summary_index_setting.enable` 只能是布尔值 `true` 或 `false`。
- 当 `enable` 是 `null` 时，后端无法判断这是“开启摘要索引”还是“关闭摘要索引”，所以校验失败。

后端允许的形态应是以下之一：

```json
"summary_index_setting": {
  "enable": false
}
```

或：

```json
"summary_index_setting": {
  "enable": true,
  "model_name": "模型名称",
  "model_provider_name": "模型供应商"
}
```

也可以不传 `summary_index_setting`。

处理建议：

- 如果不需要摘要自动生成，在页面上明确关闭摘要自动生成，让请求传 `enable: false`，或不传该字段。
- 如果页面开关状态异常，可以尝试把摘要自动生成打开再关闭一次，让前端状态从 `null` 变成明确的 `false`。
- 如果要开启摘要自动生成，则需要选择可用的生成模型，让 `enable: true` 时同时带上 `model_name` 和 `model_provider_name`。
- 第一轮 RAG 学习建议保持摘要自动生成关闭，避免多一个变量影响分段、索引和检索观察。

实际排查记录：

- 第一次创建知识库并一次性导入四个文件时，摘要自动生成默认关闭，未手动改动，可以正常点击“预览块”并预览 chunk。
- 四个文件导入成功后，再往同一个知识库追加新文件时，追加文档页面看不到“摘要自动生成”配置项。
- 但从浏览器请求体可以看到，追加文档时仍然传出了 `summary_index_setting.enable: null`。
- 该 `null` 值导致后端校验失败，无法完成 indexing estimate。
- 进入知识库设置，将“摘要自动生成”开关打开一次再关闭一次后，再回到文本预览页面，可以正常预览 chunk。

结论：

- 首次创建导入流程和后续追加文档流程可能使用了不同的前端状态来源。
- 追加文档流程在某些情况下会继承一个未规范化的摘要配置状态，即 `enable: null`。
- 通过在知识库设置中显式切换一次开关，可以把状态固化为明确的 `false`，从而绕过该问题。

## 1.7 使用 Q&A 分段

截图中“使用 Q&A 分段”处于关闭状态，语言为 Chinese Simplified。

含义：

- Dify 会尝试把文档整理成问答对形式。
- 更适合 FAQ、客服知识库、标准问答文档。

当前建议：

- 当前 `dify-rag-lab/docs/` 是学习笔记和实验记录，不是标准 FAQ。
- 第一轮不建议开启。
- 如果后续整理出 FAQ 文档，可以单独测试 Q&A 分段。

## 1.8 预览块

“预览块”用于在真正处理前查看切片效果。

截图中右侧预览显示：

- 文档 `01-chat-assistant/api.md` 被切成多个 chunk。
- 可以看到每个 chunk 的字符数。
- 出现了多个很短的 chunk。

使用方法：

- 导入前先点“预览块”。
- 检查标题是否和正文分离过度。
- 检查代码块是否被切碎。
- 检查是否出现大量短 chunk。

当前建议：

- 如果短 chunk 很多，但后续检索效果仍可接受，可以先不调整。
- 如果检索经常命中标题而不是正文，再优化切片策略。

## 2. 索引方式

截图中索引方式选择的是“高质量”。

## 2.1 高质量

含义：

- 调用 Embedding 模型处理文档，实现更精确的语义检索。
- 能帮助 LLM 生成更高质量答案。
- 处理成本和时间高于经济模式。

当前适合：

- 目标是学习 RAG 的真实语义检索效果。
- 已接入火山方舟 `embeddingversion`。
- 文档数量很少，成本可控。

注意：

- 使用高质量模式进入嵌入后，截图提示无法切换回经济模式。
- 选择前应确认 Embedding 模型配置可用。

## 2.2 经济

含义：

- 每个数据块使用约 10 个关键词进行检索。
- 不消耗 token。
- 检索准确性较低。

适合场景：

- 快速低成本试用。
- 文档少、关键词非常明确。
- 不想调用 Embedding 模型。

当前不建议：

- 本阶段目标是学习向量化和语义检索，因此应使用高质量模式。

## 3. 检索设置

检索设置决定用户问题进入知识库后，如何从 chunk 中找出最相关内容。

## 3.1 向量检索

含义：

- 先把用户问题转成查询向量。
- 再和知识库 chunk 的向量进行相似度匹配。
- 返回语义上最相似的文本分段。

适合：

- 语义相似但关键词不完全一致的问题。
- 例如用户问“为什么 API 没用最新提示词”，文档里写的是“需要发布更新，API 才使用新提示词”。

优点：

- 能理解语义相近。
- 适合自然语言问答。

缺点：

- 依赖 Embedding 模型质量。
- 对专有名词、代码路径、精确接口名可能不如关键词检索稳定。

## 3.2 全文检索

含义：

- 索引文档中的词汇。
- 用户查询时，返回包含这些词汇的文本片段。

适合：

- 精确关键词。
- API 路径。
- 配置项名称。
- 专有标识。

示例：

```text
retriever_resources
conversation_id
message_end
DIFY_APP_API_KEY
```

优点：

- 对精确词命中很稳。
- 不依赖语义理解。

缺点：

- 如果用户换一种说法，不包含原文关键词，可能召回不到。

## 3.3 混合检索

截图中选择的是“混合检索”，也是推荐方式。

含义：

- 同时执行全文检索和向量检索。
- 再通过权重设置或 rerank 模型进行重排序。
- 从两类结果中选择最匹配用户问题的片段。

当前适合：

- 学习文档中既有自然语言解释，也有 API 路径、字段名、配置名。
- 例如既要搜“发布机制为什么要点发布更新”，也要搜 `message_end`、`conversation_id`、`DIFY_APP_API_KEY`。

当前建议：

- 第一轮保持混合检索。
- 它能兼顾语义问题和关键词问题。

## 3.4 权重设置

截图中选择的是“权重设置”，而不是 Rerank 模型。

含义：

- 手动设置语义检索和关键词检索的权重比例。
- Dify 根据这个比例融合两类检索结果。

截图中的权重是：

```text
语义 0.7
关键词 0.3
```

含义：

- 语义检索占主要权重。
- 关键词检索作为补充。

当前适合：

- 大多数问题是自然语言提问。
- 但文档里仍然有接口名、字段名等关键词需要保留召回能力。

后续实验：

- 问自然语言问题时，观察是否命中解释性内容。
- 问精确字段时，例如 `message_end`，观察是否能命中 API 记录。
- 如果精确字段命中差，可以提高关键词权重。

## 3.5 Rerank 模型

截图中 Rerank 模型未选择。

含义：

- 先召回一批候选 chunk。
- 再用重排序模型根据用户问题重新排序。
- 通常能提升最终命中的准确性。

适合：

- 文档较多。
- 初次召回结果噪声较高。
- 对命中准确率要求高。

当前建议：

- 第一轮不启用 Rerank。
- 先减少依赖，只验证 Embedding + 混合检索。
- 如果后续召回结果不稳定，再接入 Rerank 模型。

## 3.6 Top K

截图中 Top K 是：

```text
3
```

含义：

- 最多返回 3 个最相关的 chunk。
- 这些 chunk 会作为上下文提供给 LLM。

影响：

- Top K 越小，上下文越聚焦，但可能漏掉相关信息。
- Top K 越大，召回更全面，但可能引入噪声并增加 token 成本。

当前建议：

- 第一轮保持 Top K = 3。
- 对当前学习文档来说，3 个 chunk 通常够用。
- 如果问题需要跨多个文档综合回答，可以提高到 5。

## 3.7 Score 阈值

截图中 Score 阈值开关关闭，输入框显示 `0.5` 但未启用。

含义：

- 如果开启，低于阈值的召回结果会被过滤。
- 例如阈值为 0.5，则相似度低于 0.5 的 chunk 不返回。

当前建议：

- 第一轮保持关闭。
- 先观察 Dify 默认会召回什么。
- 如果发现无关问题也强行召回，可以开启 Score 阈值过滤低相关片段。

