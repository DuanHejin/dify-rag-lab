# RAG 真正变准，是从我不再迷信 Rerank 开始的

知识库能正常召回以后，我一开始以为，接下来主要就是调模型。

比如换更好的 Embedding。

比如接一个更强的 Rerank。

比如调 Top K。

但真正测下来，我发现最影响效果的，反而是一个更基础的问题：

chunk 切得好不好。

这件事很容易被忽略。

因为 Dify 的知识库导入流程做得很顺。

上传文档。

选择分段规则。

预览 chunk。

点击处理。

等状态变成可用。

整个流程看起来很自动。

但 RAG 效果的起点，恰恰就在这些自动生成的 chunk 里。

如果 chunk 本身切得不合理，后面再怎么调 Rerank，都很难彻底补回来。

## 一开始我以为是混合检索不够好

最早我用几个固定问题测试：

```text
Top K 设置为 3 代表什么？
分段重叠长度是什么意思？
Dify 最小镜像升级流程是什么？
docker compose 和 docker-compose 有什么区别？
summary_index_setting enable 为 null 为什么会报错？
```

全文检索能命中一些。

向量检索有时相关性不够。

混合检索一开始也不稳定。

于是我自然想到：

是不是需要 Rerank？

后来接入了 Jina Rerank。

效果确实提升明显。

一些问题能够把最相关的段落排到第一。

这说明 Rerank 是有用的。

但继续看召回结果，我发现还有一个问题：

有时候第一条确实是相关的。

但内容不完整。

比如问：

```text
分段重叠长度是什么意思？
```

命中的 chunk 是：

```text
1.4 分段重叠长度
截图中的分段重叠长度是：
```

它命中了标题。

但没有完整解释。

真正解释“分段重叠长度有什么作用”的内容，可能在后面的 chunk 里。

这时候就算 Rerank 把它排第一，也不能解决答案不完整的问题。

因为候选 chunk 本身就不完整。

## 问题不只是 \n\n 太碎

一开始我以为问题是：

```text
\n\n 分段太碎
```

Markdown 里空行很多。

标题和正文之间有空行。

段落和列表之间有空行。

代码块前后也有空行。

如果直接按 `\n\n` 切，确实容易切得很碎。

但后来我发现，问题比这个更准确一点。

实际是两层切分叠加：

```text
第一层：按段落分段
第二层：单段超过最大长度后继续硬切
```

当时最大长度类似：

```text
1024 characters
```

如果一个小节内容超过 1024，就会被拆成两段。

第一段往往包含标题和关键词。

第二段可能包含真正完整的解释、注意事项或例子。

检索时，用户问题更容易命中第一段。

但第一段不一定包含完整答案。

第二段因为关键词少，反而可能漏召回。

这就出现了很典型的情况：

命中是命中了。

但命中的不是最适合回答的完整内容。

## 换切分规则后，效果明显变好

后来我重新调整切分规则。

不再盲目用 `\n\n` 按普通段落切。

而是更倾向于保留 Markdown 小节的完整性。

目标是让一个 chunk 尽量包含：

```text
标题
定义
解释
注意事项
例子
```

而不是只包含：

```text
标题
前半句话
```

重新切分后，同样的问题再测，准确性明显提升。

这让我对 RAG 调优有了一个很明确的判断：

如果命中标题但答案不完整，优先查切片。

不要马上换模型。

不要马上调 Rerank。

先看 chunk 有没有把完整语义单元切开。

## Top K 不是越大越好

调 RAG 时很容易动 Top K。

Top K 越大，召回候选越多。

看起来似乎更保险。

但实际不是这么简单。

Top K 太小：

```text
可能漏掉相关内容
```

Top K 太大：

```text
会引入噪声
增加 token 成本
让模型看到不必要的上下文
```

我在 API 验证时有一次结果很典型。

问题是：

```text
Dify 最小镜像升级流程是什么？
```

返回了 3 条 `retriever_resources`。

第一条分数很高：

```text
score = 0.6939131
document_name = dify-thread-context.md
```

第二条只有：

```text
score = 0.2346732
```

第三条更低：

```text
score = 0.00046479
```

第一条已经足够回答问题。

后两条更像补充甚至噪声。

这说明，Top K 不应该固定迷信一个值。

要结合场景观察：

如果第一条足够准确，可以考虑降低 Top K。

如果问题容易分散，可以提高 Top K，再交给 Rerank。

## Rerank 有用，但不是万能

我接入了两个 Rerank 方向：

```text
Jina reranker-v3
qwen3-rerank
```

Jina 的效果比较明显。

在一些问题上，它能把最相关的段落排到第一。

qwen3-rerank 也确实被调用成功。

我在阿里云百炼后台看到额度发生变化。

而且返回结果顺序也和普通权重排序不同。

比如同一个问题：

```text
分段重叠长度是什么意思？
```

权重排序是：

```text
36 -> 4 -> 16 -> 9 -> 19 -> 11 -> 45
```

qwen3-rerank 是：

```text
36 -> 16 -> 19 -> 11 -> 4 -> 45 -> 9
```

说明它确实重排了。

但整体改善没有 Jina 明显。

这给我的结论是：

不同 Rerank 模型效果会有差异。

调用成功，不代表效果一定好。

Rerank 能做的是：

```text
在已召回候选里重新排序
```

它不能做的是：

```text
凭空找回没有召回的 chunk
修复被切坏的 chunk
补全被切断的上下文
```

所以 Rerank 是后处理。

切片质量是前提。

## 怎么判断 Rerank 是否真的生效

我还踩了一个小坑。

页面上我已经选择了 Jina Rerank。

但 Network 请求体里仍然是：

```json
"reranking_enable": false
```

同时又带着：

```json
"reranking_mode": "reranking_model",
"reranking_model": {
  "reranking_model_name": "jina-reranker-v3"
}
```

这看起来很矛盾。

后来我发现，原因是我一直在复用历史召回测试。

Dify 的召回测试历史会保留当次测试的 `retrieval_model` 快照。

从历史记录里继续测试，可能沿用旧的开关状态。

重新新建一次召回测试后，请求体才变成：

```json
"reranking_enable": true
```

并且 Rerank 真正生效。

所以判断 Rerank 是否启用，不能只看有没有 `reranking_model`。

要看：

```text
reranking_enable 是否为 true
```

这是一个很容易忽略的细节。

## 现在我对 RAG 调优的顺序

经历这一轮以后，我现在不会一上来就换模型。

我会按这个顺序看：

第一，文档内容是否适合检索。

有没有标题、定义、解释和例子。

第二，chunk 是否完整。

有没有把一个语义单元硬切成两段。

第三，检索方式是否匹配文档类型。

术语多的文档，全文检索很重要。

第四，Top K 是否合适。

候选太少会漏，候选太多会噪。

第五，再看 Rerank。

Rerank 用来提升候选排序，而不是修复源头问题。

这个顺序对我很重要。

因为它让我不再把 RAG 效果问题都归因到模型上。

有时候不是模型不聪明。

而是你给它的 chunk 不完整。

## 这一阶段的结论

RAG 真正变准，不是靠某一个参数。

而是靠一整条链路变好：

```text
文档写法
切片规则
最大长度
重叠长度
检索方式
Top K
Rerank
Prompt
```

这其中，切片是最容易被低估的。

如果切片不合理，后面每一步都在补救。

如果切片合理，全文、向量、混合检索和 Rerank 才有发挥空间。

这次调完以后，我对 RAG 的理解又前进了一步：

RAG 不是把文档塞给模型。

RAG 是把文档处理成适合被检索、适合被引用、适合被模型使用的上下文。

下一步，我把这个知识库接进 Chat Assistant。

看看真正应用回答时，`retriever_resources` 会怎么返回。

这一步，RAG 才从“知识库能搜”进入“应用能用”。
