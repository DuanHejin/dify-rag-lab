# 我用 Dify 搭了一个求职聊天助手，才发现聊天框只是最外层

把 Dify 在本地跑起来之后，我做的第一个应用，是一个很简单的 Chat Assistant。

名字也很普通：

```text
简单的求职聊天助手
```

这个名字没有什么产品感。

但对我来说，它很适合作为第一个实验。

因为我刚好处在重新整理职业方向的阶段。

前面做 SuperAgentConsole 的时候，我已经把 Agent Run、Tool Router、Skill Workflow、SSE、执行回放这些东西跑了一遍。

那些东西更偏底层运行时。

而 Chat Assistant 更像一个用户真正会接触到的 AI 应用入口。

它看起来很简单：

用户输入一句话。

模型返回一段回答。

页面把回答展示出来。

但这次我不想只看“能不能聊”。

我更想看清楚，一个成熟平台里的聊天助手，到底由哪些部分组成。

## 从一个最小提示词开始

我给这个助手写的第一版提示词很短：

```text
你是一个求职准备助手，请根据用户输入，用中文给出清晰、可执行的建议。
```

这不是一个复杂 prompt。

没有角色细节，没有长篇约束，也没有复杂格式。

但我希望先从最小可用开始。

如果一开始就写一大段提示词，很容易分不清：

到底是 Dify 的配置生效了？

还是 prompt 本身太强？

所以第一轮，我只验证几个基础问题：

```text
提示词是否生效？
变量是否能传入？
调试预览是否可用？
多轮对话是否保留上下文？
API 调用是否和页面表现一致？
```

这些才是我更关心的。

一个 AI 应用不能只在页面里能跑。

它还要能通过 API 被外部系统调用。

否则它就只是平台里的一个配置，而不是可以接入真实产品的能力。

## 调试与预览，比我想象中重要

创建应用之后，我先在 Dify 的调试与预览里测试。

第一轮问题很简单：

```text
我准备面试前端开发岗位，只有 3 天时间，应该怎么准备？
```

当时我给应用配置了一个变量：

```text
job_type = 前端开发
```

模型返回了一份三天准备计划。

它会按天拆：

第一天准备 HTML / CSS / JS 基础。

第二天准备框架、算法和工程化。

第三天复盘项目、模拟面试和准备反问。

从效果上看，这已经像一个可用的求职助手了。

但我更在意的是另一个点：

调试预览不是随便聊一聊。

它是验证应用配置的第一层入口。

在这里，我可以看到：

提示词是否生效。

变量是否参与了生成。

多轮对话是否能沿用上下文。

模型参数调整后回答是否变化。

这和我自己做 SuperAgentConsole 时的 Run Detail 有点像。

只不过 Dify 的调试预览更偏产品配置验证。

我的 Run Detail 更偏执行过程追踪。

这两个东西关注点不同，但目标类似：

不要让 AI 应用变成黑盒。

## 发布更新这个动作不能忽略

我后来改了一次提示词。

加了一句：

```text
每次回答开头都输出【求职助手V2】。
```

然后我直接用 API 调了一次。

结果返回里没有这个标记。

一开始我以为是不是 API 没走最新配置。

后来才确认：

Dify 里修改提示词后，需要点击发布更新。

不发布，API 仍然使用旧版本配置。

发布以后，再调用 API，回答开头才出现：

```text
【求职助手V2】
```

这个机制很合理。

页面调试可以是草稿态。

API 调用应该走发布态。

否则一个线上应用会因为随手改 prompt 而立刻影响外部用户。

对我来说，这也是成熟平台的一个细节：

配置和发布是分开的。

这和我自己项目里的“本地改代码”和“线上部署”其实是同一个思路。

不是改了就生效。

而是要经过一次明确发布。

## API 调通后，聊天助手才真正变成能力

页面能聊只是第一步。

真正让我觉得它像一个应用能力，是 API 调通之后。

我调用的是：

```text
POST /v1/chat-messages
```

blocking 模式下，接口会一次性返回完整回答。

请求里可以传：

```json
{
  "inputs": {
    "job_type": "前端开发"
  },
  "query": "我主要薄弱在项目表达和算法，这两块怎么安排？",
  "response_mode": "blocking",
  "conversation_id": "上一轮 conversation_id",
  "user": "abc-123"
}
```

返回里有几个重要字段：

```text
answer
conversation_id
message_id
metadata.usage
metadata.retriever_resources
```

当时还没有接知识库，所以 `retriever_resources` 是空数组。

这也很正常。

因为那一阶段还只是普通聊天助手。

真正重要的是，我通过 `conversation_id` 验证了多轮对话。

第一次请求不传 `conversation_id`。

Dify 返回一个新的 `conversation_id`。

第二次请求带上它。

模型就能接着上一轮上下文继续回答。

这和我自己项目里的 Conversation / Message 概念是能对上的。

只不过 Dify 已经把这套东西封装成了 App API。

## Streaming 让我重新看了一遍 SSE

然后我又测试了 streaming。

把请求里的：

```json
"response_mode": "blocking"
```

改成：

```json
"response_mode": "streaming"
```

接口就会持续返回事件。

每个事件里带一小段 `answer`。

类似：

```json
{
  "event": "message",
  "answer": "3"
}
```

最后会有：

```json
{
  "event": "message_end",
  "metadata": {
    "usage": {}
  }
}
```

这和我之前做 SuperAgentConsole 时处理 SSE 的经验很接近。

前端不能等完整回答回来再展示。

而是要边接收边渲染。

同时还要处理：

```text
message
message_end
error
task_id
conversation_id
message_id
```

这让我有一种很明确的对照感。

Dify 的 streaming event，是平台给出的标准事件。

SuperAgentConsole 的 AgentEvent，是我自己定义的运行事件。

一个偏用户回答流。

一个偏 Agent 执行过程流。

这两者以后可以互相参考。

## 模型参数不是玄学

我还试了温度参数。

同一个问题：

```text
简单说说前端开发在 AI 盛行的背景下，未来的职业方向应该是什么。
```

我分别测试了：

```text
temperature = 0
temperature = 0.2
temperature = 0.8
```

结果很明显。

温度低的时候，回答更稳定、更收敛。

温度高的时候，表达更发散，方向也更丰富。

这不是一个新知识。

但在 Dify 里通过同一个应用去反复测试，会更直观。

我也意识到，模型参数应该跟应用场景绑定。

如果是求职建议助手，回答应该清晰、可执行、稳定。

那温度就不应该太高。

如果是创意写作或头脑风暴，可以适当放开。

参数不是为了调着玩。

它应该服务应用目标。

## 日志和监测让我看到平台闭环

测试完几轮以后，我去看 Dify 的日志与标注。

里面能看到之前的对话记录。

再看监测页面，能看到：

```text
过去 7 天会话数
活跃用户数
token 消耗
token 速度
延迟
```

这一步让我意识到：

一个 AI 应用如果只是能回答，还不够。

它还要能观察。

能知道用户问了什么。

能知道模型答了什么。

能知道成本是多少。

能知道速度怎么样。

这和我之前接 CLS 日志的感受是一样的。

真正可运行的产品，一定要有观测能力。

否则出了问题，只能靠感觉猜。

## 这一阶段我学到什么

做完这个简单 Chat Assistant 后，我对 Dify 的第一印象更清楚了。

它不是一个聊天 UI。

它至少把这些能力组织到了一起：

```text
Prompt 配置
变量输入
调试预览
发布更新
多轮会话
blocking API
streaming API
日志记录
监测指标
模型参数
```

从使用者角度看，这些是页面配置。

从工程角度看，它们对应的是一个 AI 应用的基础运行闭环。

而我自己的 SuperAgentConsole，也在做类似的事情。

只是切入点不同。

Dify 从平台配置出发。

SuperAgentConsole 从 Agent Runtime 和执行过程可解释性出发。

这两者没有谁替代谁。

它们更像两个视角。

一个让我看到成熟平台怎么把能力产品化。

一个让我继续理解底层执行链路怎么设计。

下一步，我开始看 Dify 的知识库。

也就是 RAG。

因为聊天助手只是让模型回答问题。

而知识库要解决的是：

模型如何基于我自己的资料回答问题。

这一步会更接近企业私有知识库助手。
