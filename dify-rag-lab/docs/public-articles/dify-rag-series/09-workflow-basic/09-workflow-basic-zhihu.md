# Dify Workflow 实战：它和 Chatflow 的区别到底在哪里？

学完 Chatflow 之后，我继续做了 Dify Workflow。

一开始我以为两者差不多。

都是画布。

都是节点。

都可以连 LLM。

但实际做完一个最小 Workflow 后，我发现它们的定位差异很明显。

```text
Chatflow 面向对话。
Workflow 面向一次性任务。
```

## 为什么要单独学 Workflow

Chatflow 已经可以做很多事情。

比如：

- 用户输入
- 知识库检索
- LLM 回答
- IF/ELSE 分支
- 多轮会话

但它的入口始终是用户对话。

Workflow 的入口不是一段自然语言 query，而是一组输入字段。

这更像一个任务表单。

例如这次我做的实验是：

```text
输入岗位方向、准备天数、薄弱点
输出一份面试准备计划
```

这个场景不一定需要聊天。

用户只要提交参数，系统返回结果即可。

这就是 Workflow 更适合的地方。

## 当前 Workflow 结构

我创建的 Workflow 应用叫：

```text
求职准备 Workflow
```

节点结构是：

```text
开始（用户输入）
↓
LLM：提取准备重点
↓
LLM 2：生成准备计划
↓
输出
```

这个结构很小。

但已经能覆盖 Workflow 的几个核心能力：

- Start 输入变量
- LLM 节点处理
- 上下游变量引用
- End 输出
- 页面调试

## Start 输入变量

Start 节点配置了三个字段：

```text
job_type：岗位类型，文本，必填
days：天数，数字，必填
weak_points：薄弱项目，文本，非必填
```

测试输入：

```text
job_type = 前端开发
days = 3
weak_points = 算法
```

这里和 Chatflow 最大的不同是：

Chatflow 通常接收：

```text
query
```

Workflow 接收：

```text
inputs
```

这直接影响应用形态。

Chatflow 适合“你一句我一句”的对话。

Workflow 适合“给定输入，执行流程，返回结果”的任务。

## LLM1：只负责提取准备重点

第一个 LLM 节点叫：

```text
提取准备重点
```

它不是直接生成最终计划，而是先做分析。

输出结构包括：

```text
1. 备考优先级
2. 最需要补齐的能力
3. 不建议投入太多时间的内容
```

例如当输入是：

```text
前端开发，3 天，算法薄弱
```

它会把重点放到：

- 前端高频算法
- JS/CSS/浏览器基础复盘
- 项目经历整理
- 避免复杂冷门算法

这个节点的价值是把问题先压缩成“准备重点”。

后续节点再基于它生成完整计划。

## LLM2：基于上一步输出生成计划

第二个 LLM 节点叫：

```text
生成准备计划
```

它引用第一个节点的输出：

```text
{{提取准备重点.text}}
```

然后按天生成计划。

这一步验证的是 Workflow 的核心能力：

```text
上游节点输出可以作为下游节点输入。
```

如果用工程视角理解，Workflow 中每个节点都像一个步骤。

步骤之间通过变量传递上下文。

## End 节点为什么重要

Workflow 最终返回什么，不是自动决定的。

它由 End 节点配置。

这次配置是：

```text
answer = 生成准备计划.text
```

所以最终运行结果中，调用方只需要关注 `answer`。

这和普通函数有点像。

内部可以有多个步骤。

但最终要有明确返回值。

## 调试时的一个细节

我发现单独运行某个 LLM 节点，和从 Start 开始跑完整流程，结果可能不完全一样。

原因很简单。

单节点运行时，需要手动补变量。

全链路运行时，变量来自 Start 节点真实传递。

所以如果要验证变量引用是否正确，最好从 Start 节点开始跑完整流程。

这个经验在 Workflow 调试里很重要。

## think 标签和下游引用

豆包模型返回的内容里会包含多个：

```text
<think>...</think>
```

Dify 页面会把它们渲染成可折叠块。

这对展示没有影响。

但如果下游节点引用上游 LLM 的 `text`，这些 think 内容也会一起带入。

当前实验里不影响结果。

但如果后续要做更干净的流程，可以考虑：

- 上游节点改用结构化输出
- 中间加代码节点清洗文本
- 在下游 Prompt 中明确忽略 think 内容

## Workflow 的适用场景

这轮实验之后，我对 Workflow 的理解是：

它适合确定输入和输出的一次性任务。

例如：

- 根据表单生成计划
- 根据文档生成摘要
- 根据字段生成邮件
- 批量处理结构化内容
- 后台自动化流程

它不适合的场景是强多轮对话。

如果用户需要不断追问、修正、上下文延续，Chatflow 更合适。

## 总结

Workflow 和 Chatflow 的差异可以这样理解：

```text
Chatflow：
用户 query 驱动，适合多轮对话。

Workflow：
输入变量驱动，适合一次性任务。
```

这也是我这一阶段最大的收获。

不是所有 AI 应用都应该做成聊天框。

有些需求，本质就是一个任务。

对这种需求来说，Workflow 反而更清楚。
