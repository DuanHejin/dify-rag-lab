# 学完 Chatflow 后，我用 Workflow 做了一个一次性任务编排

做完 Chatflow V2 之后，我原本以为 Workflow 应该差不多。

毕竟它们都有画布。

都有节点。

都有 LLM。

也都能连线。

但真正新建 Workflow 后，我发现两者的入口感完全不一样。

Chatflow 是从用户的一句话开始。

Workflow 更像从一组明确的输入参数开始。

也就是说，Chatflow 面向对话。

Workflow 面向任务。

这个差异听起来很简单。

但只有自己配一遍 Start 输入、LLM 节点和 End 输出后，才会真正有感觉。

## 先做一个最小 Workflow

这次我没有继续接知识库。

因为这一阶段的目标不是 RAG。

而是验证 Workflow 的基本编排能力。

我建了一个应用：

```text
求职准备 Workflow
```

画布里一共四个节点：

```text
开始（用户输入）
↓
LLM：提取准备重点
↓
LLM 2：生成准备计划
↓
输出
```

这个流程非常简单。

第一个 LLM 只做分析。

第二个 LLM 基于分析生成计划。

输出节点返回最终结果。

它不像 Chatflow 那样围绕多轮对话展开。

更像一次明确的处理任务。

## Start 节点不是 query，而是输入字段

Workflow 的 Start 节点里，我配置了三个输入字段：

```text
job_type：岗位类型，文本，必填
days：天数，数字，必填
weak_points：薄弱项目，文本，非必填
```

测试输入是：

```text
job_type = 前端开发
days = 3
weak_points = 算法
```

这个地方和 Chatflow 很不一样。

Chatflow 的入口通常是：

```text
query = 用户说的话
```

Workflow 的入口更像：

```text
inputs = 一组表单字段
```

这也决定了它更适合做一次性任务。

比如：

```text
输入岗位、天数、薄弱点
↓
生成准备计划
```

这种任务本来就不一定需要多轮对话。

## 第一个 LLM 只提取准备重点

第一个 LLM 节点我命名为：

```text
提取准备重点
```

它的 Prompt 大意是：

```text
你是一个求职准备分析助手。
请根据用户输入的岗位方向、准备时间和薄弱点，提取本次面试准备的核心重点。

岗位方向：前端开发
准备时间：3天
薄弱点：算法

请输出：
1. 备考优先级
2. 最需要补齐的能力
3. 不建议投入太多时间的内容
```

这个节点不负责生成完整计划。

它只做分析。

实际输出里，它会围绕“前端开发 + 3 天 + 算法薄弱”整理出重点：

```text
第一优先级：前端面试高频算法专项突击
第二优先级：前端核心高频基础考点快速复盘
第三优先级：过往项目经历的亮点梳理
```

这一步让我想到自研项目里的 Skill step。

一个步骤只负责一件事。

不要让它既分析又生成最终答案。

## 第二个 LLM 引用第一个 LLM 的输出

第二个 LLM 节点叫：

```text
生成准备计划
```

它会引用第一个 LLM 的输出：

```text
上一步准备重点：
{{提取准备重点.text}}
```

然后生成按天拆分的计划。

这样流程就变成：

```text
Start 输入
↓
LLM 1 分析重点
↓
LLM 2 生成计划
↓
End 输出
```

这一步的关键不是模型回答得多好。

而是验证：

```text
上游节点的输出，可以被下游节点继续使用。
```

这也是 Workflow 最基本的价值。

## 单独运行节点和全链路运行不完全一样

调试时我遇到一个小现象。

我单独运行第二个 LLM 节点时，手动输入变量，结果有点不稳定。

后来我从 Start 节点开始跑全链路。

在用户输入里填：

```text
job_type = 前端开发
days = 3
weak_points = 算法
```

流转到第二个节点时，就能正确接收到这些输入。

这让我意识到，Workflow 调试时要区分：

```text
单节点调试
```

和：

```text
全链路调试
```

单节点调试适合看一个节点本身。

全链路调试更适合验证变量传递。

如果要确认真实运行效果，还是应该从 Start 开始跑。

## End 节点决定最终返回什么

Workflow 里还有一个很关键的点：

最终返回值不是自动等于最后一个 LLM 的所有内容。

而是由 End 节点配置决定。

我把输出配置成：

```text
answer = 生成准备计划.text
```

所以最终结果里只返回这个字段。

这和 Chatflow 的 Answer 节点有点像。

但 Workflow 的 End 更像一个明确的返回结构。

这对后续 API 调用很重要。

因为调用方要知道从哪里取结果。

## think 标签被 Dify 前端兼容展示了

这次我还观察到一个细节。

豆包模型返回的 `text` 里有多个：

```text
<think>...</think>
```

在原始输出中，它们是普通文本的一部分。

但 Dify 页面会把它们渲染成可折叠的“已深度思考”块。

因为同一个 text 里有多个 think 片段，页面上每个折叠块右侧时间显示都是：

```text
0.0s
```

这个看起来像前端兼容展示逻辑的计时限制。

不影响最终输出。

但它提醒我一件事：

如果下游节点继续引用上游 LLM 的 `text`，这些 think 内容也会一起传下去。

后面如果要优化，可以考虑：

```text
让上游 LLM 使用结构化输出
或者增加一个清洗节点
```

## 这一阶段我对 Workflow 的理解

Workflow 不是“没有聊天框的 Chatflow”。

它更像一个任务编排器。

它的核心是：

```text
输入字段
↓
节点处理
↓
变量传递
↓
最终输出
```

这类形态很适合：

```text
批处理
表单生成
结构化分析
后台自动化任务
固定流程任务
```

如果我要做一个“根据岗位、天数、薄弱点生成计划”的功能，Workflow 比 Chatflow 更直接。

因为用户不需要对话。

他只需要提交参数。

系统给结果。

这一步让我把 Dify 的几个应用形态分得更清楚：

```text
Chat Assistant：快速聊天
Chatflow：带流程的对话
Workflow：一次性任务编排
Knowledge：可复用知识能力
```

理解这些差异，比单纯会点页面更重要。

因为真正做产品时，第一步不是选节点。

而是判断：

这个需求，到底应该是对话，还是任务。
