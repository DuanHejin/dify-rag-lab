# 我把自己的 Dify 学习笔记导入知识库，才真正理解 RAG 不是“上传文档就完事”

Chat Assistant 跑通之后，我开始看 Dify 的知识库。

也就是 RAG。

在这之前，我对 RAG 的理解还比较概念化。

大概知道它是：

```text
用户提问
↓
从知识库检索相关内容
↓
把检索结果交给大模型
↓
模型基于资料回答
```

这个链路听起来很顺。

但真正开始在 Dify 里做的时候，我才发现，RAG 的难点不在“上传文档”。

而在上传之后的一整套细节。

文档怎么切？

Embedding 模型怎么选？

向量库里到底有没有数据？

全文检索和向量检索有什么区别？

混合检索是不是一定更好？

Rerank 什么时候需要？

回答里怎么知道引用了哪段资料？

这些问题不跑一遍，很难有感觉。

## 我没有用官方文档做知识库

一开始我想过，直接把 Dify 源码或者官方文档导进去。

但后来觉得不合适。

因为我的目标不是测试 Dify 能不能检索大规模资料。

我想验证的是：

我自己的学习过程，能不能被整理成一个可搜索、可问答的知识库。

所以我没有导入整个 Dify 源码。

我导入的是自己项目里的学习文档。

比如：

```text
dify-thread-context.md
dify-learning-plan.md
chat-assistant-api.md
knowledge-rag-plan.md
knowledge-rag-config-notes.md
```

这些文档记录了我这段时间的真实学习路径：

本地怎么部署 Dify。

Chat Assistant 怎么调 API。

提示词怎么发布更新。

知识库配置项是什么意思。

RAG 召回测试遇到过什么问题。

这样做有一个好处：

我知道正确答案应该在哪里。

如果问：

```text
Dify 最小镜像升级流程是什么？
```

我知道答案应该命中 `dify-thread-context.md`。

如果问：

```text
分段重叠长度是什么意思？
```

我知道应该命中 `knowledge-rag-config-notes.md`。

这比导入一堆陌生资料更适合学习。

因为我能判断召回到底准不准。

## Embedding 不是聊天模型

做知识库之前，我先遇到了 Embedding 模型的问题。

一开始我已经接入了豆包聊天模型。

但知识库需要的是 Embedding。

聊天模型负责生成回答。

Embedding 模型负责把文本转成向量。

它们不是一回事。

这个区别很重要。

RAG 里至少有三类模型能力：

```text
LLM：负责最终回答
Embedding：负责向量化和语义检索
Rerank：负责候选结果重排
```

我后来在火山方舟里接入了可用的 Embedding 模型。

Dify 里显示为：

```text
embeddingversion
```

接入以后，知识库才能做高质量索引。

这一步让我意识到：

AI 应用不是一个模型解决所有问题。

一个看起来简单的问答应用，背后可能有多个模型协作。

## 文档导入以后，不等于 RAG 成功

我创建了一个知识库：

```text
dify学习知识库
```

导入了 5 个 Markdown 文档。

每个文档最后都显示可用。

chunk 数量大概是：

```text
knowledge-rag-config-notes.md：169
chat-assistant-api.md：66
dify-learning-plan.md：47
knowledge-rag-plan.md：40
dify-thread-context.md：104
```

看到“全部可用”的时候，我一度以为可以开始问答了。

但很快发现，事情没那么简单。

文档状态可用，只说明：

文档导入完成。

切片完成。

索引流程完成。

它不代表：

检索一定能命中。

命中的 chunk 一定完整。

页面一定能正确展示。

最终回答一定好。

RAG 不是“上传文档”这个动作。

RAG 是从文档到回答的一整条链路。

每一环都可能出问题。

## 第一次看分段，我就意识到切片很关键

Dify 在导入文档时，会进入“文本分段与清洗”。

这里可以配置：

```text
分段标识符
分段最大长度
分段重叠长度
预处理规则
索引方式
检索方式
Top K
Score 阈值
Rerank
```

一开始我对这些配置只是知道名字。

但真正看 chunk 预览时，感觉就很明显了。

如果 chunk 切得太碎，检索可能只命中标题。

如果 chunk 太长，又会带入太多噪声。

如果标题和解释分到不同 chunk，模型可能只拿到问题的一半。

这时你再调 Top K、权重、Rerank，都只能缓解。

源头切坏了，后面很难补。

这也是我后来调优 RAG 时最深的一个感受：

RAG 效果首先取决于 chunk 质量。

模型不是魔法。

检索也不是魔法。

它们都依赖你给进去的材料是否适合被检索。

## 全文检索、向量检索和混合检索

在 Dify 的召回测试里，我主要看了三种方式：

```text
全文检索
向量检索
混合检索
```

全文检索更像关键词搜索。

比如问：

```text
Top K 设置为 3 代表什么？
```

如果文档里就有 `Top K`，全文检索很容易命中。

向量检索更偏语义。

它会把问题和 chunk 都转成向量，然后找语义上相近的内容。

但对我的学习笔记来说，里面有很多英文术语：

```text
Top K
chunk
docker-compose
retriever_resources
reranking_enable
```

这种内容不一定适合纯语义检索。

关键词也很重要。

混合检索看起来最理想。

它结合全文和向量。

但我实际测试下来，一开始效果并不稳定。

后来加了 Jina Rerank，混合检索效果才明显变好。

这让我对 RAG 有了一个更现实的理解：

检索方式没有绝对最优。

要看你的文档类型和问题类型。

学习笔记、配置说明、操作记录这种文档，关键词往往非常关键。

## 第一次看到 retriever_resources

在 Chat Assistant 还没接知识库时，API 返回里：

```text
metadata.retriever_resources = []
```

接入知识库后，再问相关问题，里面就会出现命中的资料。

比如问：

```text
Dify 最小镜像升级流程是什么？
```

返回里能看到：

```text
dataset_name: dify学习知识库
document_name: dify-thread-context.md
score: 0.6939131
content: 4.4 Dify 最小镜像升级流程...
```

这对我来说很重要。

因为它把 RAG 从黑盒里拉出来了一点。

我不只是看到模型回答。

我还能看到：

模型回答之前，系统检索到了哪些文档。

哪些 chunk 被带入上下文。

每个 chunk 的分数是多少。

这和我在 SuperAgentConsole 里做 AgentEvent 的目标很接近：

让系统过程可观察。

AI 应用最怕的是：

回答看起来很对，但你不知道它依据什么。

`retriever_resources` 至少能告诉我：

这次回答有没有真的用到知识库。

用了哪些资料。

资料是否相关。

## 无关问题也要测

RAG 不能只测相关问题。

还要测无关问题。

我问了一个：

```text
今天北京天气怎么样？
```

返回里：

```text
retriever_resources = []
```

回答也没有硬套知识库。

而是说明：

知识库里没有北京今日天气资料。

它作为求职准备助手，不支持实时天气查询。

这个结果是符合预期的。

因为一个知识库助手不应该什么都往知识库上套。

如果没有相关资料，就应该明确说没有。

这比强行编一个答案更重要。

## 这一阶段的收获

做完第一轮知识库实验后，我对 RAG 的理解具体了很多。

以前我觉得 RAG 是：

```text
上传文档，然后让模型基于文档回答
```

现在我更愿意把它理解成：

```text
文档整理
↓
切片
↓
清洗
↓
Embedding
↓
索引
↓
检索
↓
Rerank
↓
上下文构造
↓
LLM 回答
↓
引用来源观察
```

每一层都会影响最终效果。

Dify 的价值，是把这条链路产品化了。

但产品化不等于不用理解。

如果不了解切片、检索、Rerank、引用来源这些概念，就很容易把 RAG 当成一个上传按钮。

而真正做过一次后，我才知道：

上传只是开始。

能不能搜准。

搜到的内容够不够完整。

模型有没有基于资料回答。

这些才是 RAG 真正要验证的东西。

下一篇，我会记录这次 RAG 学习里最折腾的一段：

明明知识库显示可用，为什么一开始就是搜不出来。

这段排查从页面报错，一直查到了 Network、API 日志和 Weaviate。
