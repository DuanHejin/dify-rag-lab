# Chatflow 进阶：为什么要给 AI 应用加参数提取和 IF/ELSE？

在 Chatflow V1 中，我已经跑通了一个基本的 RAG 对话流程。

它的结构是：

```text
用户输入
↓
知识检索
↓
LLM
↓
回复
```

这个流程能回答问题。

但它还不够像一个真正可控的应用。

原因是：它缺少入口判断。

## 只靠最终 LLM 判断，会有什么问题

如果所有用户输入都直接进入知识检索和 LLM，会出现几类问题。

第一类是信息不完整。

例如：

```text
我想准备面试
```

这个问题方向是对的，但信息不够。

它缺少岗位、准备时间、薄弱点。

第二类是问题无关。

例如：

```text
北京天气怎么样？
```

这个问题和当前应用目标无关。

第三类是完整问题。

例如：

```text
Dify 最小镜像升级流程是什么？
```

或者：

```text
我是前端开发，还有 3 天面试，算法和项目表达比较弱。
```

这些可以继续进入后续链路。

所以我需要一个前置步骤，先判断用户输入属于哪一类。

## 参数提取节点做什么

我在 Chatflow V2 中加入了参数提取节点。

它不负责最终回答。

它只负责把自然语言输入转换成结构化对象。

结构大致是：

```json
{
  "intent": "job_prepare",
  "job_type": "前端开发",
  "days": 3,
  "weak_points": ["算法", "项目表达"],
  "is_complete": true
}
```

这里最关键的是两个字段：

```text
intent
is_complete
```

`intent` 用来判断用户意图。

当前支持：

```text
job_prepare
dify_learning
out_of_scope
```

`is_complete` 用来判断这个问题是否足够进入下一步。

## is_complete 不能只看字段是否为空

一开始我以为，`is_complete` 只要看 `job_type` 和 `days`。

但后来发现这样不够。

因为 Dify 学习类问题不需要岗位和天数。

例如：

```text
Dify 最小镜像升级流程是什么？
```

这是一个完整问题。

但它没有 `job_type`。

所以 `is_complete` 的规则应该结合意图：

```text
intent = dify_learning
→ is_complete = true

intent = job_prepare 且 job_type / days 足够
→ is_complete = true

intent = job_prepare 但信息不足
→ is_complete = false

intent = out_of_scope
→ is_complete = false
```

这一步让我意识到，结构化输出不是简单抽字段。

它其实是在为后续流程提供可判断的状态。

## IF/ELSE 分支如何设计

参数提取之后，我用 IF/ELSE 节点做分流。

逻辑是：

```text
IF structured_output.is_complete = true
  → 知识检索

ELIF structured_output.intent 包含 job_prepare
  → 补充信息回复

ELSE
  → 暂不支持回复
```

对应的三个分支是：

1. 完整问题进入知识检索和 LLM。
2. 求职准备但信息不够，提示用户补充岗位、计划时间、薄弱项目。
3. 无关问题直接兜底。

这个逻辑看起来非常像代码。

但在 Dify 里，它通过可视化节点完成。

## 追问不是从中间节点继续执行

这里还有一个容易误解的点。

当用户说：

```text
我想准备面试
```

系统回复：

```text
信息不够明确，请补充信息，如岗位、计划时间、薄弱项目。
```

用户下一轮再说：

```text
前端开发，3 天，算法和项目表达比较弱
```

这不是从“补充信息”节点继续往后走。

而是一次新的用户输入。

它会重新从 Start 节点开始执行。

也就是说，Chatflow 的追问更像：

```text
多轮对话中的新一轮流程执行
```

而不是：

```text
在画布中间暂停后继续往下跑
```

这个理解很重要。

否则很容易误以为要从补充信息节点再连回参数提取节点。

## 为什么这比纯 Prompt 更稳

当然，也可以在最终 LLM 的 Prompt 里写：

```text
如果信息不够，请提示用户补充。
如果问题无关，请拒绝回答。
```

但这样做有两个问题。

第一，判断不够稳定。

第二，所有问题都已经进入了后续节点。

而 IF/ELSE 的好处是：

```text
在进入知识库和最终 LLM 之前，就完成分流。
```

这会让流程更可控。

对于业务边界清楚的问题，确定性分支比 Prompt 更可靠。

## 这一阶段的结论

Chatflow V2 给我的最大启发是：

AI 应用不是所有东西都应该交给大模型判断。

更合理的分工是：

```text
确定性判断：交给 IF/ELSE
自然语言理解：交给参数提取 LLM
知识问题：交给 RAG
最终表达：交给回答 LLM
```

这样做的结果是：

- 完整问题可以继续进入 RAG
- 信息不足问题可以要求补充
- 无关问题可以直接兜底
- 大模型不需要承担所有流程控制责任

这也是我理解 Chatflow 的一个关键转折。

它不是单纯“拖节点调用模型”。

它是在帮我把 AI 应用拆成：

```text
理解
判断
检索
生成
回复
```

几个更清楚的环节。
