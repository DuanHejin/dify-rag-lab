# 我给 Chatflow 加了 IF/ELSE，才发现 AI 应用不能什么都交给大模型

Chatflow V1 跑通以后，我做的下一步，是复制一个 V2。

名字不重要。

重要的是，我想验证一件事：

```text
一个对话式 AI 应用，能不能不要每一步都让大模型自由发挥？
```

之前的流程是：

```text
用户输入
↓
知识检索
↓
LLM
↓
回复
```

这条链路能跑。

但它有一个问题。

不管用户说什么，系统都尽量往知识库和 LLM 里送。

用户问 Dify，可以回答。

用户问面试，也可以回答。

但如果用户只说：

```text
我想准备面试
```

信息其实不够。

如果用户问：

```text
北京天气怎么样？
```

这个问题和当前应用目标也无关。

这些情况不应该全部交给最终 LLM 去判断。

所以我开始给 Chatflow 加分支。

## 先加一个参数提取节点

我在 V2 里新增了一个参数提取节点。

它的任务不是回答问题。

而是把用户输入拆成结构化信息。

我让它输出：

```json
{
  "intent": "job_prepare",
  "job_type": "前端开发",
  "days": 3,
  "weak_points": ["算法", "项目表达"],
  "is_complete": true
}
```

这里有几个字段很关键。

`intent` 用来判断用户意图。

我目前只关心三类：

```text
job_prepare
dify_learning
out_of_scope
```

`job_type` 是岗位方向。

`days` 是准备时间。

`weak_points` 是薄弱点。

`is_complete` 是当前信息是否足够进入下一步。

这一步看起来像一个小功能。

但它实际上改变了整个 Chatflow 的控制方式。

用户输入不再直接进入最终回答。

而是先变成一个可以判断的对象。

## is_complete 的含义变了

一开始，我对 `is_complete` 的理解比较简单。

如果用户提供了岗位和天数，就认为完整。

比如：

```text
我是前端开发，还有 3 天面试，算法和项目表达比较弱。
```

这当然完整。

但后来我发现，V2 不只是做求职准备。

它还要支持 Dify / RAG 学习类问题。

比如：

```text
Dify 最小镜像升级流程是什么？
```

这个问题没有 `job_type`。

也没有 `days`。

但它是一个完整问题。

所以 `is_complete` 不能只看岗位和天数。

后来我把规则改成：

```text
如果 intent = dify_learning，则 is_complete = true
如果 intent = job_prepare 且 job_type / days 足够，则 is_complete = true
如果 intent = job_prepare 但信息不足，则 is_complete = false
如果 intent = out_of_scope，则 is_complete = false
```

这个调整很小。

但它让流程从“字段完整性判断”，变成了“意图 + 字段完整性判断”。

## IF/ELSE 节点开始接管流程

参数提取之后，我加了一个 IF/ELSE 节点。

分支是这样的：

```text
IF is_complete = true
  → 走知识检索分支

ELIF intent 包含 job_prepare
  → 回复：信息不够明确，请补充信息，如岗位、计划时间、薄弱项目。

ELSE
  → 回复：暂不支持此类对话，请咨询面试，RAG相关知识。
```

这个逻辑很像写代码。

只不过它不是写在 TypeScript 里。

而是拖在 Dify 的画布上。

如果用户输入：

```text
我想准备面试
```

参数提取会判断：

```json
{
  "intent": "job_prepare",
  "is_complete": false
}
```

于是走补充信息分支。

如果用户接着说：

```text
前端开发，3 天，算法和项目表达比较弱
```

下一轮会从头重新进入流程。

这一次参数完整，就进入知识检索和 LLM 回答。

这里我也修正了一个理解。

所谓“追问”，不是在补充信息节点后面再画一根线连回参数提取节点。

用户再次输入，本来就会从 Start 节点重新开始。

这才符合 Chatflow 的运行方式。

## 无关问题不再进入知识库和 LLM

我还测了无关问题。

比如：

```text
北京天气怎么样？
```

参数提取节点会把它归为：

```text
out_of_scope
```

然后 IF/ELSE 直接走兜底回复：

```text
暂不支持此类对话，请咨询面试，RAG相关知识。
```

这一步我觉得很重要。

因为它说明，有些判断没有必要交给最终 LLM。

如果业务边界非常明确，完全可以用确定性分支拦住。

这样做有几个好处。

第一，回答更稳定。

第二，减少无意义的知识库检索。

第三，降低模型自由发挥带来的不可控。

## 命中知识库时，仍然走原来的 RAG 链路

完整问题仍然会进入 RAG。

比如：

```text
Dify 最小镜像升级流程是什么？
```

它会进入知识检索。

然后 LLM 基于检索结果回答。

回答开头也换成了：

```text
【Chatflow-RAG-V2.0】
```

这说明 V2 的分支没有破坏原来的 RAG 能力。

它只是把入口变得更严格。

原来是：

```text
所有问题都尝试回答
```

现在是：

```text
先判断问题是否适合回答
再决定走哪条链路
```

## 这一步让我重新理解“低代码工作流”

以前我对这种可视化流程有一点偏见。

我会觉得拖节点像是在页面上写代码。

复杂了之后可能不如直接写代码。

这个判断没有错。

但做完 Chatflow V2 后，我也看到它的价值。

对于一些非常清晰的业务分支，比如：

```text
信息不足
无关问题
完整问题
```

用 IF/ELSE 直接表达，其实很直观。

它不需要让大模型每次都猜。

也不需要在 Prompt 里堆很多“如果怎样就怎样”。

确定性的部分，就交给确定性的节点。

需要生成和总结的部分，再交给大模型。

这可能是我这一阶段最大的收获。

AI 应用不是把所有判断都塞给大模型。

也不是把所有流程都写死。

更合理的做法是：

```text
能确定的，用规则。
需要理解和生成的，用模型。
需要访问外部能力的，用工具。
```

Chatflow V2 只是一个很小的实验。

但它让我开始真正理解，为什么 AI 应用的工程设计，不只是 Prompt。

还包括流程边界。
