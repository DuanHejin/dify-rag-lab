# 做完自己的 Agent 项目后，我为什么开始学习 Dify？

SuperAgentConsole 跑通之后，我有一种很微妙的感觉。

一方面，我确实完成了一个阶段。

从最早的想法，到 Nuxt3 项目搭建，再到 Docker 镜像、GHCR、GitHub Actions、K3S、ConfigMap、Secret、HTTPS、CLS 日志、真实大模型接入、Agent Run、Tool Router、Skill Workflow、执行回放页面，这条链路我一步一步走下来了。

它不再只是一个本地 demo。

域名能访问。

登录能跑。

数据库能写。

日志能查。

Agent 可以进入真实模型调用。

前端能看到一次 Run 的执行过程。

从“重新部署自己”这个系列的角度看，这算是一个很重要的节点。

因为我不只是写了一个页面，也不只是调了一个大模型接口。

我真正把一个 AI / Agent 产品从本地推到了线上。

但另一方面，项目越往后做，我越能感觉到一件事：

自己从 0 搭一套东西，很容易陷入自己的视角。

我知道我的 Tool Router 怎么写。

我知道我的 Skill Workflow 怎么跑。

我知道 AgentEvent 为什么要一条条落库。

我知道 Run Detail 页面为什么要把每一步展示出来。

这些设计对我来说都是有原因的。

但它们到底是不是一种成熟 AI 应用平台里常见的设计？

有没有更通用的叫法？

有没有更标准的产品形态？

一个真正被很多人使用的平台，会怎么处理应用类型、知识库、工作流、API、日志和监测？

这些问题，光靠继续写自己的项目，很难回答。

所以在 SuperAgentConsole 第一阶段完成后，我没有马上继续往里堆功能。

我决定先停下来，找一个成熟平台做参照。

这个平台，就是 Dify。

## 为什么是 Dify？

我之前对 Dify 的印象，比较模糊。

大概知道它是一个 AI 应用开发平台，可以配置聊天助手、工作流、知识库、Agent，也可以接不同模型。

但这只是概念层面的知道。

真正开始做 SuperAgentConsole 之后，我再看 Dify，感觉就不一样了。

因为我已经亲手做过一遍类似的东西。

我知道一个聊天应用背后不只是一个输入框。

它至少会涉及：

- 用户输入
- 模型调用
- 多轮会话
- SSE 流式响应
- 工具调用
- 运行过程记录
- 日志排查
- API 访问
- 部署环境

如果再往 RAG 方向走，还会涉及：

- 文档导入
- 文本切片
- Embedding
- 向量库
- 检索
- Rerank
- 引用来源
- 无关问题兜底

这些东西，我在自己的项目里已经碰到了一部分。

但 Dify 是一个成熟平台。

它把这些能力产品化了。

这对我来说很有价值。

我不是想用 Dify 替代自己的项目。

更不是想把之前做的 SuperAgentConsole 推倒重来。

我想做的是对照学习。

看看一个成熟平台如何组织 AI 应用。

看看它把哪些能力做成页面配置，哪些能力暴露成 API，哪些能力藏在运行时里。

再反过来看自己的项目：

哪些地方是已经走在正确方向上的？

哪些地方只是我自己的实现习惯？

哪些地方未来应该补齐？

这就是我开始学习 Dify 的原因。

## 这不是另起炉灶，而是给自己的项目找参照物

做技术项目时，有一个很容易出现的问题：

只要自己能跑通，就觉得理解了。

但跑通和理解之间，中间还差一层。

比如我在 SuperAgentConsole 里做了 Agent Run。

一次运行会经历：

```text
用户输入
↓
模型规划
↓
工具调用
↓
结果回填
↓
最终回答
```

我把这些过程拆成事件，落库，再展示到执行回放页面里。

这在我的系统里叫 AgentEvent、Run Detail、Tool Router、Skill Workflow。

但到了 Dify 里，它可能不是这么叫。

它可能叫日志、追踪、工作流节点、工具调用、会话消息。

名字不同，抽象也不同。

如果我只看自己的命名，就容易把自己的实现当成唯一方式。

而学习 Dify 的意义，是让我看到另一套抽象。

不是为了照搬。

而是为了校准。

这就像做完一个自己的小框架后，再去看 Vue、React、Nuxt，不是为了否定自己的代码，而是为了理解成熟框架为什么这样设计。

Dify 对我来说，就是 AI 应用平台领域里的一个参照物。

## 第一步，先把 Dify 在本地跑起来

学习一个平台，最好的方式不是先看一堆文章。

而是先把它跑起来。

我把 Dify clone 到本地：

```bash
git clone --depth 1 https://github.com/langgenius/dify.git
```

本地目录大概是：

```text
~/personalProjects/dify-rag-lab/dify
```

Docker Compose 目录是：

```text
~/personalProjects/dify-rag-lab/dify/docker
```

启动之后，浏览器访问：

```text
http://localhost:8080
```

然后完成管理员账号初始化。

这一步本身不复杂。

但它让我马上意识到，Dify 和我之前写的单体应用不一样。

它不是一个前端项目加一个后端接口。

它是一组服务。

启动以后，背后会有：

- web
- api
- worker
- db
- redis
- nginx
- sandbox
- vector database

也就是说，Dify 本身就是一个比较完整的平台型应用。

它的复杂度不在某一个页面里，而在整套服务协同里。

这和我部署 SuperAgentConsole 时的感受很像。

一个 AI 应用真正上线以后，问题不会只出现在代码里。

它会出现在数据库、日志、容器、网络、模型调用、镜像仓库、服务器地域这些地方。

前面我自己的项目已经给我上过一课。

Dify 只是把这件事再次放大给我看。

## Docker Compose 不是附属知识

以前我会把 Docker Compose 当成一种“部署工具”。

需要的时候查一下命令，不需要的时候就放在一边。

但这次学习 Dify，我对它的感受更具体了。

Docker 是用来运行单个容器的。

Docker Compose 是用来编排一组容器的。

Dify 这种平台，天然就适合用 Docker Compose 来启动。

因为它不是一个服务。

它需要数据库存配置和应用数据。

需要 Redis 做缓存和队列。

需要 worker 处理异步任务。

需要向量库支撑知识库检索。

需要 nginx 做统一入口。

需要 sandbox 隔离某些执行环境。

所以当我执行：

```bash
docker-compose up -d
```

它背后启动的不是一个“项目”，而是一套系统。

这个过程其实也提醒我：

如果以后继续做自己的 Agent 平台，不能只盯着业务代码。

真正的平台能力，一定会落到这些基础设施上。

## 源码和镜像，不是一回事

在部署 Dify 时，我遇到的第一个重要认知点，是源码和镜像的关系。

我本地 clone 了 Dify 源码。

于是很容易产生一个误解：

我现在运行的 Dify，是不是就在跑本地这些 `api/`、`web/` 源码？

答案是否定的。

默认 Docker Compose 启动时，真正运行的是 `docker-compose.yaml` 里指定的镜像。

比如：

```yaml
image: langgenius/dify-api:1.14.1
image: langgenius/dify-web:1.14.1
```

也就是说，容器里跑的是官方已经打包好的镜像。

本地源码只是放在那里。

你改了本地源码，只要没有重新 build 成自己的镜像，运行中的 Dify 就不会受影响。

这个点对我特别重要。

因为它刚好对应两种完全不同的使用方式。

如果只是学习 Dify，或者部署官方 Dify：

重点是 Docker Compose 和官方镜像。

如果要二开 Dify：

才需要修改源码，构建自己的镜像，再让服务器使用自己的镜像。

这两件事不能混在一起。

我之前做 SuperAgentConsole 时，整个镜像构建和发布链路是自己搭的：

```text
GitHub Actions
↓
构建 Docker 镜像
↓
推送到 GHCR
↓
服务器拉取镜像
↓
K3S 更新服务
```

所以再看 Dify，我会更敏感地意识到：

源码是开发材料。

镜像才是运行实体。

数据卷则是系统状态。

这三个东西必须分清。

## 第一次升级 Dify，也是在补部署认知

后来我在测试知识库 RAG 时，遇到了一个页面渲染问题。

知识库检索其实有结果。

但页面展示时报错。

继续查以后发现，官方新版本已经修复了相关问题。

于是我需要把 Dify 从 1.14.1 升级到 1.14.2。

一开始我还在想，要不要把本地源码切到官方 tag。

但很快又回到前面的认知：

我现在运行的是镜像。

如果只是为了升级正在运行的 Dify，最小动作不是切源码，而是改镜像版本。

也就是把 `docker-compose.yaml` 里的核心镜像从：

```yaml
langgenius/dify-api:1.14.1
langgenius/dify-web:1.14.1
```

改成：

```yaml
langgenius/dify-api:1.14.2
langgenius/dify-web:1.14.2
```

然后执行：

```bash
docker-compose down
docker-compose pull
docker-compose up -d
```

这里还有一个小插曲。

我一开始照着一些说明用了：

```bash
docker compose up -d
```

结果本机提示：

```text
docker: unknown command: docker compose
```

后来确认，我当前环境里可用的是旧版独立命令：

```bash
docker-compose
```

所以命令要写成：

```bash
docker-compose up -d
```

这个细节不大，但很真实。

很多时候我们以为自己在学一个平台，实际过程中会被这些环境差异绊一下。

如果不记录，下次还会再踩。

## 升级不只是 web 变了就行

升级以后，我用：

```bash
docker-compose images
```

看了一下实际运行的镜像。

结果发现一开始并不是所有服务都升级到了 1.14.2。

有些服务已经是 1.14.2。

但 api、api_websocket、worker_beat 里还残留 1.14.1。

这说明我只改了一部分镜像版本。

Dify 的 api、worker、worker_beat 等服务，可能都使用 `langgenius/dify-api` 这个镜像。

如果只改其中一处，就会出现混合版本。

这件事让我想起线上部署时的很多问题。

服务看起来启动了，不代表版本完全一致。

页面能打开，不代表所有后台任务都已经更新。

对平台型应用来说，升级一定要确认实际运行的容器和镜像。

最后我把所有核心服务统一到 1.14.2，再重新拉取和重建容器，问题才真正解决。

## volumes 不能乱删

升级前，我做了备份：

```bash
cp docker-compose.yaml docker-compose.yaml.bak
cp .env .env.bak
tar -cvf volumes-backup.tgz volumes
```

这里最重要的是 `volumes`。

因为本地 Dify 的数据库、上传文件、向量库等数据，都和它有关。

容器可以删除再建。

镜像可以升级。

但 `volumes` 不能随便删。

这和我之前做 SuperAgentConsole 时对 PVC、MySQL 数据迁移的理解是一样的。

应用服务本身是可替换的。

真正不能轻易丢的，是数据状态。

如果只是学习环境，删了也就是重新来一遍。

但如果是企业私有部署，删错数据卷就是事故。

所以我在自己的学习文档里专门记了一条：

不要轻易删除 `volumes`。

它不是临时缓存，而是本地 Dify 的状态仓库。

## 接入模型以后，平台感才出来

Dify 跑起来后，我接入了豆包模型。

这一步让我看到 Dify 的第一层平台抽象：

模型供应商管理。

在自己写 demo 时，我们经常直接在代码里配置：

```text
base_url
api_key
model
```

但在 Dify 里，它被抽象成模型供应商和模型能力。

后面创建 Chat Assistant、知识库、Workflow、Chatflow 时，都可以复用这些模型配置。

再往后做 RAG 时，我又接触到 Embedding 模型和 Rerank 模型。

这时候就更明显了：

一个 AI 应用不是一个模型包打天下。

LLM 负责生成回答。

Embedding 负责把文本转成向量。

Rerank 负责对候选结果重新排序。

这些能力如果散落在代码里，很容易混乱。

Dify 把它们放到统一的模型供应商体系里，学习起来会更直观。

这也是成熟平台值得学习的地方。

它不是把复杂性消灭了。

而是把复杂性放到了合适的位置。

## 这一篇真正想记录什么

如果只看操作，这一篇很简单。

无非是：

clone Dify。

Docker Compose 启动。

初始化管理员账号。

接入豆包模型。

升级镜像。

备份 volumes。

但对我来说，这不是一篇“Dify 安装教程”。

它更像是 SuperAgentConsole 第一阶段之后的一次回看。

我通过 Dify 重新确认了几个问题。

第一，AI 应用平台一定是多服务协同。

页面只是入口，背后还有 api、worker、数据库、缓存、向量库和任务系统。

第二，源码、镜像、数据卷必须分清。

学习官方平台时跑镜像。

二开时改源码并构建自己的镜像。

数据卷是状态，不能当垃圾文件处理。

第三，成熟平台的价值不只是功能多。

它更重要的价值，是提供了一套抽象。

比如模型供应商、应用类型、知识库、工作流、API、日志与监测。

这些抽象会反过来帮助我检查自己的项目。

第四，学习 Dify 不是从 SuperAgentConsole 逃开。

恰恰相反。

这是为了更好地理解 SuperAgentConsole 下一步该怎么走。

自研项目让我知道一个系统怎么从 0 到 1 长出来。

Dify 让我看到一个成熟平台如何组织类似能力。

这两件事放在一起，才更完整。

## 接下来要看 Chat Assistant

Dify 跑起来以后，下一步最自然的是 Chat Assistant。

因为它最接近一个普通用户对 AI 应用的第一印象：

打开页面。

输入问题。

得到回答。

但这一次我不想只停留在“能不能聊”。

我更想看清楚：

提示词在哪里生效？

变量怎么传？

调试预览和发布更新是什么关系？

blocking API 和 streaming API 有什么区别？

`conversation_id` 如何支撑多轮对话？

日志、标注、监测能看到什么？

这些问题，刚好也能和我自己的 SuperAgentConsole 对照起来。

所以下一篇，我会用 Dify 创建一个简单的求职聊天助手。

从页面配置，到 API 调用，再到流式响应和多轮会话。

不是为了做一个复杂助手。

而是为了用最小例子，把 Dify 的聊天应用链路跑通。

SuperAgentConsole 是我自己从 0 搭的一套系统。

Dify 是我用来校准认知的一面镜子。

接下来，我会一边跑 Dify，一边继续回头看自己的项目。

看看哪些地方可以借鉴。

哪些地方应该坚持自研。

哪些能力，是下一阶段必须补上的。
