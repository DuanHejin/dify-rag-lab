# Dify RAG 调优后，我发现最关键的不是 Rerank，而是 chunk 切得对不对

知识库能正常召回之后，我开始调效果。

一开始我以为主要是模型问题。

比如：

```txt
Embedding 是否合适
Rerank 是否足够强
Top K 是否太小
混合检索权重是否合理
```

但实际测下来，我发现更基础的问题是：

```txt
chunk 切得是否合理
```

如果 chunk 从源头就不完整，后面的 Rerank 只能重排候选，不能把断掉的上下文补回来。

## 1. 现象：命中标题，但答案不完整

测试问题：

```txt
分段重叠长度是什么意思？
```

一开始能命中相关 chunk。

但命中的内容类似：

```txt
1.4 分段重叠长度
截图中的分段重叠长度是：
```

这个 chunk 是相关的。

但它不完整。

真正解释“分段重叠长度有什么作用”的内容，可能在另一个 chunk 里。

这就出现了一个问题：

```txt
召回命中了
但命中的不是最适合回答的完整内容
```

Rerank 把它排第一，也只能说明它最相关。

但它依然不完整。

## 2. 问题不只是 \n\n 太碎

一开始我以为问题是：

```txt
\n\n 分段太碎
```

Markdown 里空行很多。

如果按 `\n\n` 切，确实容易把标题、正文、列表、代码块拆散。

但后来发现，问题更准确地说是：

```txt
按段落切分 + 最大长度硬切
```

例如最大长度是：

```txt
1024 characters
```

当一个语义小节超过这个长度时，会被继续切成两段。

第一段可能包含标题和关键词。

第二段可能包含完整解释和注意事项。

检索时，第一段更容易命中。

但回答时，第二段可能更有价值。

这就是问题所在。

## 3. 换切分规则后，准确性明显提升

后来我重新调整切分规则。

目标是尽量保留完整语义单元。

一个 chunk 里最好包含：

```txt
标题
定义
解释
注意事项
例子
```

而不是：

```txt
标题
半句话
```

重新分段后，同样问题的召回准确性提高很多。

这说明当前主要瓶颈不是模型，而是切片。

我的结论是：

```txt
如果召回命中标题但答案不完整，优先检查 chunk 切分，而不是马上换模型。
```

## 4. Top K 的取舍

Top K 控制返回多少个候选 chunk。

Top K 太小：

```txt
容易漏召回
```

Top K 太大：

```txt
容易引入噪声
增加 token 成本
```

例如问：

```txt
Dify 最小镜像升级流程是什么？
```

API 返回 3 条 `retriever_resources`。

第一条：

```txt
score = 0.6939131
document_name = dify-thread-context.md
```

第二条：

```txt
score = 0.2346732
```

第三条：

```txt
score = 0.00046479
```

这种情况下，第一条已经足够回答。

后两条更像补充或噪声。

所以 Top K 不是越大越好。

它要根据问题和文档类型调。

## 5. Jina Rerank 和 qwen3-rerank 对比

我测试了 Jina Rerank 和 qwen3-rerank。

Jina 的效果更明显。

在一些问题上，可以把最相关段落排到第一。

qwen3-rerank 也确实被调用成功。

阿里云百炼后台能看到额度变化。

而且返回顺序也发生了变化。

例如：

权重排序：

```txt
36 -> 4 -> 16 -> 9 -> 19 -> 11 -> 45
```

qwen3-rerank：

```txt
36 -> 16 -> 19 -> 11 -> 4 -> 45 -> 9
```

说明 qwen3-rerank 不是没生效。

它确实重排了。

只是当前材料和问题上，效果没有 Jina 明显。

所以调用成功不等于效果一定好。

模型之间有实际效果差异。

## 6. Rerank 不是万能的

Rerank 的作用是：

```txt
对已经召回的候选 chunk 重新排序
```

它不能：

```txt
找回没有召回的 chunk
修复被切坏的 chunk
自动补全相邻上下文
```

所以如果正确内容根本没有进入候选集，Rerank 没法救。

如果候选 chunk 本身不完整，Rerank 也只能把不完整的 chunk 排到前面。

这就是为什么切片比 Rerank 更基础。

## 7. 如何判断 Rerank 是否真的生效

我还遇到过一个细节。

页面上明明选择了 Rerank 模型。

但 Network 请求体里还是：

```json
"reranking_enable": false
```

同时又带着：

```json
"reranking_mode": "reranking_model",
"reranking_model": {
  "reranking_model_name": "jina-reranker-v3"
}
```

后来发现，是因为我复用了历史召回测试。

Dify 的召回测试历史会保留当次 `retrieval_model` 快照。

如果从历史记录继续测试，可能沿用旧开关。

重新新建召回测试后，才看到：

```json
"reranking_enable": true
```

所以判断 Rerank 是否生效，重点不是看有没有 `reranking_model`。

而是看：

```txt
reranking_enable 是否为 true
```

## 8. 我现在的 RAG 调优顺序

现在我会按这个顺序调：

```txt
1. 看文档内容是否适合检索
2. 看 chunk 是否完整
3. 看切分规则是否导致语义断裂
4. 看检索方式是否匹配文档类型
5. 调 Top K
6. 再接 Rerank
7. 最后看是否需要换 Embedding
```

不会一上来就换模型。

因为很多时候不是模型不行。

而是上下文给错了。

## 9. 结论

这次调优后，我对 RAG 的理解变成：

```txt
RAG 不是把文档塞给模型
而是把文档处理成适合被检索和引用的上下文
```

切片是整个 RAG 链路的地基。

如果 chunk 切坏了：

```txt
全文检索会命中不完整内容
向量检索会语义不足
Rerank 只能重排残缺候选
LLM 最终只能基于不完整上下文回答
```

所以 RAG 调优不要只盯模型。

先看你的 chunk。

下一步，就是把调好的知识库接入 Chat Assistant。

看最终应用 API 里 `retriever_resources` 会怎么返回。
